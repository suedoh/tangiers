# BTC audit — signal efficacy + recon health (2026-08-03)

**Scope:** BTC signal generation (`scripts/trigger-check.js`) and BTC recon/execution
(`scripts/blofin/*`, `scripts/ops/watchdog.js`, `scripts/audit/falsification.js`).
BZ!, Poly and EW are out of scope by request.

**Cohort:** `trades.json`, 814 records, 682 resolved, 76 trading days,
2026-04-13 → 2026-08-03. Accounting: `design-intent-v1` (spec 03) throughout — one
schema, no pre/post-rewrite mixing. Regime: BTC **−15.6%** over the window
(Apr +7.9%, May −3.5%, Jun −20.4%, Jul +7.3%), i.e. **≥2 regimes are present in the data.**

**Verification stack:** Wilson 95% CI · two-sided Fisher exact · BH-FDR q=0.10 ·
day-clustered bootstrap on mean R (B=10,000) · lag-1 autocorrelation with Fisher-z ·
Brier/ECE · chronological split. Ground truth = Binance public REST
(5,456×30m / 163,699×1m, zero gaps). Exchange state read read-only via en0.

---

## Verdict

The plumbing is good. The signal is not.

Measured honestly, the BTC signal has **statistically significant negative directional
skill** (43.5% symmetric hit rate, Wilson upper bound 47.3% — below a coin), and the
entry rule **destroys the payoff geometry the signal advertises** (planned 2.77:1 →
realised 0.79:1). Those two facts together set a break-even win rate of 54.7% against a
delivered 41.6%. The −13.0pp shortfall is the whole story; fees are the second-order term,
not the cause.

Separately, **four safety systems are currently degraded, and three of them report green.**

This is not a machine that catches high-probability BTC setups. It is a well-built
measurement instrument that has now measured its own signal accurately enough to say so.

# GROUP A — Tier 1 defects (provable from code / logs / git; ship without new data)

## A1 — Autotrade result is discarded by the cron exit. 23% of signals have no execution record.

`scripts/trigger-check.js:2828` fires autotrade **without awaiting it**:

```js
autotrade.autotrade({...}).then(r => { ... markExecution(signalId, ...) })
                          .catch(e => { markExecution(signalId,'dropped',...); postAutotradeDeadLetter(...) });
```

`scripts/trigger-check.js:2883` then calls `finishCron(0)` → `process.exit(0)`
(`scripts/lib/cron-exit.js:30`). The comment there reads *"whatever else libuv is still
holding is by definition work nobody is waiting on."* The autotrade promise **is** work
someone is waiting on. When main() finishes first, `.then`/`.catch` never run:
`executionStatus` is never stamped and the dead-letter alert never posts.

Autotrade takes ~5s (`firedAt` 02:40:26 → `executionAt` 02:40:31 on the 2026-08-03 signal);
the post-signal parity sidecar takes ~4–5s. It is a genuine race, and it regressed with
commit `cb38c94` (2026-07-26 20:20 UTC, the cron-exit-discipline fix — before it, the
process leaked and incidentally survived long enough).

| | signals | unstamped |
|---|---|---|
| 2026-06-15 → cb38c94 | 173 | **0** |
| cb38c94 → now | 13 | **3 (23%)** |

Two-sided Fisher exact **p = 2.7e-4**. Affected: `2026-07-28T22:50`, `2026-07-30T09:20`,
`2026-08-02T02:30`.

**Why it is a safety issue, not just telemetry.** The autotrade sequence is
entry → fetch fill → risk trim → **standalone SL** → verify → TP ladder. Exiting
mid-sequence can leave a filled entry with no stop — the exact failure Phase B.6 was
built to prevent — with no `executionStatus`, no dead-letter, and (see A2) a blind
protection invariant. Fix: `await` the autotrade promise before `finishCron`, with a
bounded timeout.

## A2 — The watchdog cannot see the recon failure that is actually happening.

`checkReconFresh()` (`scripts/ops/watchdog.js:155`) checks log freshness, then scans the
last pass for `/reconcile errors: [1-9]|resolve errors: [1-9]/`. The dominant failure
mode aborts *before* those summary lines are ever written:

```
─── BloFin reconciliation ─── 2026-08-03T06:06:07.733Z
env:     demo
instId:  (all)

unexpected: Error: blofin http 403: <!DOCTYPE html>
```

No `reconcile errors:` line exists in a 403 pass → the regex misses → `recon=ok`. The
comment at line 161 says the pattern was added because "freshness alone missed the
2026-07-04 E11000 loop" — it was written for that incident's log shape and never
generalised to the 403 class, which has been the dominant failure since 2026-07-10.

`marginLow` has the same hole and is explicitly fail-open:
`[watchdog] marginLow check unreadable (fail-open): blofin http 403` immediately
followed by `marginLow=ok`.

**Measured 403 rate per day** (480 recon cycles/day expected, all present):

| day | failed | rate |
|---|---|---|
| 2026-07-27 | 0 | 0.0% |
| 2026-07-30 | 18 | 3.8% |
| 2026-08-01 | 58 | **12.1%** |
| 2026-08-02 | 64 | **13.3%** |
| 2026-08-03 (to 06:11) | 40/124 | **32.3%** |

Accelerating. Root cause reconfirmed live, matching the 2026-07-10 diagnosis exactly:
default route is `utun5` (ProtonVPN `ch.protonvpn.mac`, Connected).

```
default route (utun5): 403
en0-bound (172.18.7.153): 200
```

Not code, not auth — Cloudflare blocking the VPN exit. The operational fix chosen on
2026-07-10 (split-tunnel / VPN-off) has regressed.

**Current exchange state is safe** — verified read-only over en0 at 06:2x UTC:
equity $1,679.12, **0 open positions, 0 pending TPSL, 0 pending orders**, protection
invariant OK. The exposure is that nothing in the automated stack could have told us that.

## A3 — Falsification Gate 2 compares two different accounting systems. It cannot pass, and it is wired to the kill switch.

`scripts/audit/falsification.js:514` takes the actual book as
`Σ t.pnlR` — post-spec-03 that is **design-intent, net-of-fee** R. The Monte Carlo books
are scored by `walk30G()` (line 310) — the **canonical** walk: full position, no fill
model, **no fees**. The header comment states both conventions on adjacent lines without
reconciling them. Scoring the same book three ways:

| scoring | actual | MC median | percentile |
|---|---|---|---|
| **shipped gate** (net pnlR vs no-fee MC) | −131.4R | +1086R | **0** |
| both sides canonical `walk30G` | +1023.4R | +1086R | **1.5** |
| both sides honest ladder + fees | −313.0R | −428R | **100** |

The comparison was valid pre-spec-03 (the ledger was canonical then too — that is the
audit's original, correct "0th percentile" finding). It broke when spec 03 changed
`pnlR` semantics on the same day (`c0371fa`) that the harness shipped (`451d8aa`), and
the harness's own `newSchema` branch shows the schema change was known.

**As shipped, Gate 2 carries no information about the signal** — it measures the
accounting delta. Consistently scored it gives opposite answers (1.5th vs 100th
percentile) depending on which convention you pick, so neither should be quoted until
the gate is rewritten to score both sides identically.

**Time-critical:** `.falsification-state.json` has `consecutiveFails: 1`. The weekly
cron (`30 8 * * 1`, Docker) fires **today at 08:30 UTC**. It will fail, reaching
2 consecutive → writes `.autotrade-disabled.json` and requires manual operator deletion.
Gate 1 fails legitimately; Gate 2 fails by construction. The trip is directionally
correct but half of its evidence is invalid.

## A4 — The 30% margin cap and the 1%-risk sizing policy are mutually unsatisfiable for 89% of signals.

Margin as a fraction of equity is `RISK_PER_TRADE_PCT / (stopFrac × LEVERAGE)`.
With `RISK_PER_TRADE_PCT=1.0`, `BLOFIN_LEVERAGE=10` (`blofin-autotrade.js:54`) and
`MARGIN_CAP_PCT` defaulting to 30 (`blofin-autotrade.js:88`), a signal is placeable only
if its stop sits **≥ 0.333%** from entry.

Measured stop distances: **p10 0.214% · median 0.216% · p90 0.342%.**

- **727 / 814 signals (89.3%) are structurally un-placeable.** Since 2026-07-01: 77.8%.
- Implied margin at the median stop: **46.3%** of equity.
- Notional-to-risk at the median stop: **463×**.

This is not a tuning question — it is two constants that cannot both hold over the
signal population the system actually generates. It is why the last 8 signals were all
skipped and **zero orders have been placed since 2026-07-27**:

```
margin cap: would use 40.7% > 30%          (2026-08-03)
margin cap: would use 40.5% > 30%          (2026-07-29)
same-direction position open (net 16)      (2026-07-30/31)
insufficient margin: ... available $43     (2026-07-26)
```

Resolving it needs an operator decision (→ B2), but the contradiction itself is provable.

## A6 — The ledger measures a strategy the executor does not trade.

Two entry conventions coexist and are never reconciled:

- **Ledger (design-intent, spec 03):** entry = the confirming 30M close;
  `riskPerUnit = |confirmedPrice − stop|`; only 682/814 signals ever confirm.
- **Executor (`blofin-autotrade`):** market order ~5s after `firedAt`, at the fire price,
  on every signal that clears the guards.

Scored on the same klines, the executor's convention is materially worse:

| | mean R/trade | day-clustered 95% CI | total |
|---|---|---|---|
| ledger (design-intent) | −0.193 | [−0.339, −0.029] | −131.4R |
| executor (fire-time entry, honest ladder + fees) | −0.385 | [−0.636, −0.120] | −313.0R |

**The headline number the operator sees understates the loss of what is actually being
executed by ~2.4×.** Spec 04 named this ("single source of P&L truth") and is marked ✅,
but the two conventions are still live simultaneously. The authoritative reconciler
(`scripts/audit/phase-d-attribution.js`) cannot currently run — it is blocked by the same
403 as A2.

# GROUP B — Tier 2 open questions (operator decision; no fix proposed)

**B1 — Keep the confirmation gate at all?** It is the mechanism behind the whole loss
(see the Mechanism section). Removing it makes the ledger match the executor (A6) and
restores the 2.77:1 geometry, but it also removes the only filter the system has. Both
options are defensible; the data does not choose.

**B2 — Which side of A4 gives way:** raise `MARGIN_CAP_PCT`, cut
`RISK_PER_TRADE_PCT`, raise leverage, or widen stops? Each has a different risk meaning.
Note the *planned* stop is ~0.216% wide = **0.65×ATR30m median, with 79.0% of signals
placing their stop inside 1×ATR30m** — i.e. inside the noise. Widening stops is the only
option that addresses both the margin contradiction and that.

**B3 — VPN policy.** The 2026-07-10 operational fix (split-tunnel / VPN-off) regressed.
The code-side `localAddress` bind was proven to work then and rejected in favour of the
operational fix. Same choice, now with evidence the operational fix does not hold.

**B4 — The +0.25R bar (carried over, still owed).** It was derived from 30m fee
economics; whether it scales with timeframe must be decided **before** re-scoring the 4h
H9-trendHiVol lead, not after.

# The mechanism — why it loses

This is the part that was not previously quantified. It is provable from the ledger alone.

**The confirmation rule requires a completed 30M close beyond planned entry. That close
lands, on average, most of the way to the first target.**

| | value |
|---|---|
| planned stop width | 0.216% of price = **0.65×ATR30m** (79.0% sit inside 1×ATR — inside the noise) |
| confirming close beyond planned entry | median **1.51 planned-R** (p75 2.68, p90 3.78) |
| `\|fill − stop\|` ÷ `\|entry − stop\|` | **2.71×** (173 pts → 468 pts; realised stop 1.81×ATR) |
| signals confirming *beyond planned tp1* | **41.2%** |
| signals confirming *beyond planned tp3* | 8.4% |
| planned ladder payoff | **2.77 : 1** |
| realised ladder payoff from the fill | **0.79 : 1** |
| fills that trip the >1.25× risk-trim | **92.8%** |

Consequences, in order:

1. **Break-even gross win rate incl. fees = 54.7%.** (avg gross win +0.850R, avg gross
   loss −0.630R, mean fee 0.179R.) Delivered: **41.6%. Shortfall −13.0pp.**
2. **Symmetric ±1×ATR30m skill = 43.5%** [39.9, 47.3] Wilson; day-clustered
   [36.4, 49.7]; ρ=0.325 → ESS 348 of 682. Below a coin, and the Wilson upper bound
   does not reach 50%.
3. **Skill rises monotonically with the barrier** — 38.1% / 43.5% / 47.2% / 49.3% /
   51.0% at k = 0.5 / 1 / 1.5 / 2 / 3. That is the signature of entering into
   short-horizon adverse drift: the entry price is systematically a local extreme in the
   wrong direction. Corroborated directly — **58.7% of fills are worse than the fire
   price**, and skill by chase quintile runs **54.7% → 46.7% → 42.3% → 45.3% → 28.4%**.
4. Fees are the coup de grâce, not the cause: gross is **−0.013R/trade**, CI
   [−0.158, +0.143] — indistinguishable from zero. Fees turn a coin into a −0.193R/trade
   bleed, and **12.7% of gross winners become net losers**.

Stability: gross R/trade by quartile −0.168 → −0.367 → −0.162 → −0.072 (Q4 is
2026-06-13→07-31). Monthly symmetric skill 41.4 / 45.0 / 42.9 / 42.4% — flat. It is not
getting better, and it is not a regime accident.

# What is working

Worth stating plainly, because most of the engineering is sound:

- **Price-time cell dedup (spec 05) works.** 72 same-day/direction/zone clusters of ≥4
  signals historically (worst: 31 on 2026-05-07); **1** since it went live 2026-07-26.
  The 2026-07-25 margin death-spiral — 16 identical `long VAL 63%` signals in one day,
  trimming 32.3 → 29 → 20.3 → 14.4 → 9.7 contracts until $43 of margin remained — is
  exactly what it now prevents.
- **The spec-03 ledger rewrite is correct and held up.** Every number in this audit was
  reproducible from it, and it is the reason the signal's failure is now visible at all.
- **Gate 1 of the falsification harness is sound** and is the only trustworthy
  edge metric the project has.
- Cron coverage is complete: 480/480 recon cycles/day, no missed BTC trigger polls,
  0 hung `trigger-check` processes (was 158 pre-`cb38c94`), pm2 stable.
- The exchange is flat and protected right now.
